# 01 - Harnesses that run and coordinate many AI coding agents

Researched 2026-11-06. Pages marked "opened" were fetched and read. Anything marked "list-only" comes from a one-line description in a curated list and was not opened. The web search budget ran out before every lead could be followed; list-only items are named at the end so a follow-up can open them.

Terms used below. A git worktree is a second checked-out folder of the same repository on its own branch, so two agents can edit without touching each other's files. A harness is the program that launches an AI agent, gives it tools and keeps it running. Headless means run from a script with no interactive screen.

Fit is judged against five problems: (1) Claude and GPT sessions colliding through handoff notes, (2) merge freezes on main, (3) duplicated work, (4) serial GitHub Actions jobs, (5) the claim-kit rule that two blind reviewers, with planted false controls, must agree. One structural point governs most verdicts. The claim kit is not a "many agents edit one codebase" problem. Each batch is a sealed packet of about 8 orders with disjoint inputs, so batches can run in parallel without merge conflicts, and the real work is dispatch, cost control, schema-checked output and keeping reviewers independent. Most tools below are built for the other problem (parallel feature work on one codebase).

CLAUDE.md says to run `python3 -I jobs/kean/kean.py search <words>` before proposing any tool or pilot. I did not touch the repo, so run that before acting on anything here.

## Part A. Gas Town and Beads

- **Gas Town** ([repo, opened](https://github.com/steveyegge/gastown); the repo now sits under the `gastownhall` organization) - Steve Yegge's workspace manager that runs 20-30 coding agents at once, mostly Claude Code, with work state stored in git. Announced January 2026.
  - Concepts (all from the opened README): **Mayor** is the main AI coordinator you talk to; **Polecats** are worker agents with a persistent identity whose sessions end when a task ends; **Convoys** bundle work items ("beads") and assign them; **Witness** watches polecats and restarts stuck ones; **Refinery** is a per-repository merge queue that runs verification and merges to main; **Deacon** is a background supervisor; **Dogs** are maintenance helpers the Deacon dispatches; **Crew** is your own clone for hands-on work; **Hooks** are worktree-based storage that survives crashes; **Rigs** wrap one git repository each. These are Yegge's own coined labels, not industry vocabulary.
  - Install needs: Git 2.20+, Go 1.26.2+, Beads `bd` 0.57.0+, sqlite3, tmux 3.0+, Dolt (installed separately on Linux), and the Claude Code CLI. Docker Compose is an alternative. Claude Code is the default runtime; Codex works with a configuration change; presets exist for Gemini, Cursor and Copilot. 18.6k stars, 1.7k forks, 379 open issues, MIT license.
  - Cost evidence: DoltHub ran it on its own repository for about an hour and reported [about $100 in Claude tokens, roughly 10 times a normal session](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/). A secondhand account says the same team's Go-to-C rewrite cost about $3,000 ([Augusteo](https://www.augusteo.com/blog/inside-gas-town/), not independently verified). [Appleton](https://maggieappleton.com/gastown) estimates Yegge himself spends at least $2,000 a month. An [HN thread](https://alt-hn.vercel.app/item/46688101) says he bought 22 Claude Max plans and was auto-banned by Anthropic's fraud detection (reported by commenters, not confirmed by me). A [Substack user](https://embracingenigmas.substack.com/p/exploring-gas-town) says heavy use can drain a large share of a Max subscription within hours.
  - Honest reviews:
    - DoltHub (measured, negative): the Mayor said all four bugs were fixed when two pull requests existed; work was committed but never pushed; Gas Town merged a pull request whose integration tests were failing and a colleague had to reset and force-push the repository; none of the four pull requests were good. Verdict: "not ready for a real codebase."
    - [Tenzin Wangdhen](https://tenzinwangdhen.com/posts/gastown-good-bad-ugly/) (hands-on, one week, then stopped): 141 orphaned Claude processes eating RAM, thin observability, "optimizes for throughput over correctness. Some work gets lost by design," agents launched with permission prompts disabled, needs tmux comfort. Kept the ideas, dropped the tool.
    - [Koziol](https://embracingenigmas.substack.com/p/exploring-gas-town) (six weeks, positive, one practitioner, no benchmarks): works for multi-project delegation; the checks that stop agents from self-grading "done" are the useful part.
    - HN commenters: Beads "keeps breaking often with each release"; one user went back to plain Markdown after two weeks; agents "don't mind changing or deleting tests instead of fixing code"; Mythical Man-Month coordination costs still apply to agents.
    - Hype versus measured: the "100-1000x" claims are hype; the only measured run is the DoltHub one, and it failed.
  - Status: Yegge's [v1.0 post](https://steve-yegge.medium.com/gas-town-from-clown-show-to-v1-0-c239d9a407ec) says early versions killed workers mid-job and lost data for weeks, and claims it is now stable. A [wiki entry](https://ericfode.github.io/agent-harness-wiki/entities/gas-city) says Gas Town is moving to maintenance mode and Gas City is the successor. [Gas City](https://yegge-ai.pages.dev/listings/welcome-to-gas-city) (April 2026) rebuilds it as a kit of parts for custom agent topologies; that page says Yegge moved all his own work to it by May 2026, and the wiki calls it "alpha-stage" and partly aspirational. A related Gas Town crypto token collapsed about 90-98% after Yegge distanced himself from it (headline-level search results only, not opened).
  - Fit: poor. It is Claude-first, optimizes throughput over correctness (the opposite of this project's standard), runs agents with permissions off, needs tmux/Go/Dolt, and its merge queue solves a code-conflict problem this project mostly does not have. Ideas worth copying without adopting the tool: a merge queue that is the only writer to main (addresses freezes), persistent role identity with throwaway sessions, and "an agent cannot mark its own work complete" (already the project's blind-review rule).
  - **Verdict: SKIP.** Maintenance mode, a failed measured trial, about $100 per hour, and a design goal that conflicts with the evidence standard.

- **Beads (`bd`)** ([repo, opened](https://github.com/gastownhall/beads)) - a command-line issue tracker for agents, with a dependency graph, `bd ready` to list unblocked work, hash-based IDs so branches do not collide, and `bd update <id> --claim` for an atomic claim. Storage is Dolt (a version-controlled SQL database); `.beads/issues.jsonl` is only an export. 28.2k stars, MIT. `bd setup` wires it into Claude Code, Codex, Cursor and Factory.
  - Evidence: HN reports above (breaks across releases, "a bad joke" codebase per one commenter). The README itself mentions a schema-version guard that blocks older binaries from opening migrated databases, which matters when Claude and GPT sessions run different checkouts.
  - Fit: the atomic claim and hash IDs target problem 3 (duplicated work). But the repository already has Kean (a register of results, questions and owner decisions) and `HANDOFF/` notes. Replacing them with a Dolt-backed tracker would add a binary, a schema-migration risk and a second source of truth, in a repository already 8.4 GB in `.git`.
  - **Verdict: WATCH.** Copy the claim-before-work idea into Kean (a small script that writes a claim file and uses a git push as the lock) instead of adopting `bd`. Naming note per CLAUDE.md: a claim-token script could be called "Tessera" (the Roman token used to prove a claim).

## Part B. Claude Code's own parallel features (all opened on code.claude.com, 2026-11-06)

- **Subagents** ([docs](https://code.claude.com/docs/en/sub-agents)) - helper agents defined as Markdown files, each with its own context window, tools and model (`model: sonnet`, `haiku`, `opus`). `isolation: worktree` gives one its own worktree. Default limits: 20 concurrent, 3 levels of nesting. `CLAUDE_CODE_SUBAGENT_MODEL` plus `_FORCE` pins every subagent to one model. Cost: tokens only, included in the plan.
  - Fit: this is already the project's "Opus coordinates, Sonnet workers" pattern. Worktree isolation helps only if a worker writes to the repository.
  - **Verdict: ADOPT NOW** (already in use; tighten with per-subagent `model` and `tools` allowlists).

- **Claude Agent SDK / headless `claude -p`** ([docs](https://code.claude.com/docs/en/headless)) - runs Claude Code from scripts. `--output-format json` returns `total_cost_usd` and a per-model breakdown; `--json-schema` forces schema-valid output in a `structured_output` field; `--max-budget-usd` caps spend; `--resume <id>` continues a session; Python and TypeScript SDKs exist. `--bare` skips hooks, plugins, CLAUDE.md and the OAuth login, and requires `ANTHROPIC_API_KEY`.
  - Fit: this is the most direct tool for the claim-kit stages (drafting CSV claims, running two reviewers). Schema output replaces fragile parsing; the budget cap bounds the $10-25 per batch; a cost record per batch feeds the Bentham plan. The pain point "cannot authenticate `claude -p` in some containers" may be avoidable by `--bare` with an API key, but that switches billing from subscription to API tokens. That is my inference from the docs, not a tested fix. Piped input is capped at 10 MB; use file paths for large evidence.
  - **Verdict: ADOPT NOW.** Wrap one driver script per stage with schema, budget cap and cost log.

- **Dynamic workflows** ([docs](https://code.claude.com/docs/en/workflows)) - Claude writes a JavaScript script that runs many subagents; the script, not Claude's context, holds the loop and intermediate results. `agent()` runs one subagent (optionally with a JSON `schema`), `pipeline()` runs one per list item, `parallel()` runs a set. Up to 16 concurrent agents by default (configurable to 256), 1,000 agents per run, resumable after a pause, saved to `.claude/workflows/` as a reusable command. Bundled `/deep-research` cross-checks claims and filters ones that fail. Available on paid plans and API; usable via `claude -p` and the SDK if a `Workflow` allow rule is set. A warning shows above 25 agents or 1.5 million projected tokens. Note: the `ultracode` keyword does not trigger in `-p` runs.
  - Evidence: Anthropic documentation only; I found no independent measurements.
  - Fit: strong for parallel claim-kit batches, with a saved script per stage and an adversarial-review step built in. Limits: every worker is a Claude model, so it cannot supply the different-family reviewer the project requires; the workflow cannot run shell commands itself (agents do), so checkers stay in the agents or in separate scripts; the cost warning is advisory, not a cap.
  - **Verdict: TRY** one pilot on a single batch, comparing cost and agreement against the current manual pipeline.

- **Agent teams** ([docs](https://code.claude.com/docs/en/agent-teams)) - one lead session and several full teammate sessions sharing a task list (file locking on claims) and mailboxes. Disabled by default behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. Docs warn: no session resume for in-process teammates, task status can lag, one team per session, no nested teams, no worktree isolation (partition files yourself), teammates are not spawned in `-p` or SDK runs. Cost: the cost page says roughly 7x tokens when teammates run in plan mode; a [blog post](https://dev.to/mathieu_kessler_8712ec765/claude-code-agent-teams-what-the-docs-dont-tell-you-1iae) says 3-4x and that file overwrite is the main failure (anecdote).
  - Fit: it is a conversation among Claude sessions, not durable coordination, and it cannot run headless. **Verdict: SKIP** for this project.

- **Agent view and background sessions** ([docs](https://code.claude.com/docs/en/agent-view)) - `claude --bg "task"` or `/bg` starts a full session without a terminal attached; `claude agents` shows all of them by state (needs input, working, completed); each edits in its own worktree under `.claude/worktrees/`. Research preview; runs on your own machine only; each session uses subscription quota; stopped by machine restart.
  - Fit: addresses serial runs for Claude-only work on one machine. It does not help GPT sessions, and the 9 GB repository makes a worktree per session heavy (the docs have a worktrees page on controlling what gets copied; I did not read it). **Verdict: TRY** only if sessions run on a machine you control.

- **Cross-session messaging** ([docs](https://code.claude.com/docs/en/cross-session-messaging)) - Claude can list and message your other Claude sessions (`ListAgents`, `SendMessage`; needs v2.1.224+). Same-machine messages go over a local socket; cloud and other-machine sessions go through Remote Control and need a claude.ai login. Plain text only. Messages count as prompts. A session in a container and one on the host cannot reach each other; two sessions inside one container can. Inbound messages cannot approve anything or change configuration.
  - Fit: could replace some handoff-note chatter between Claude sessions, but not between Claude and GPT, and most of this project's sessions probably run in separate containers (unknown to me). **Verdict: WATCH.**

- **Claude Code in the cloud and Projects** ([agents overview](https://code.claude.com/docs/en/agents), [Projects](https://code.claude.com/docs/en/claude-projects)) - parallel cloud sessions; Projects is a public beta on Pro and Max only, not Team or Enterprise. Cloud sessions keep running with your laptop off. Each would need to clone a 9 GB repository; I did not verify limits. **Verdict: WATCH.**

- **`/loop`, scheduled tasks, `/goal`** ([index](https://code.claude.com/docs/llms.txt)) - in-session repeat prompts and cloud scheduled tasks. Cheaper than inventing a loop runner, but each fire re-sends full context (cost page). **Verdict: WATCH.**

It also offers a cloud product on isolated microVMs, multiplayer workspaces, an iPhone app. The site now says "from Meta" (the company joined Meta). Closed source, desktop app appears Mac-only, pricing not stated on the pages I opened.
  - Fit: an interactive review cockpit; it does not touch serial Actions jobs, claim-kit economics or cross-family blind review. **Verdict: SKIP.**
- **Vibe Kanban** ([repo](https://github.com/BloopAI/vibe-kanban), [shutdown post](https://vibekanban.com/blog/shutdown)) - kanban board of agent workspaces. 28.1k stars. A review noted twenty tasks created twenty worktree folders (disk bloat). **Verdict: SKIP** (company dead).
- **Crystal / Nimbalyst** ([Crystal](https://github.com/stravu/crystal), [Nimbalyst review](https://rywalker.com/research/nimbalyst)) - Crystal is deprecated (February 2026). Successor Nimbalyst is a free MIT-licensed Electron app (open-sourced April 30, 2026; 795 stars in June 2026; v0.65) with a kanban board and worktree per session for Claude Code and Codex. **Verdict: SKIP** (early, interactive).
- **Claude Squad** ([repo](https://github.com/smtg-ai/claude-squad)) - terminal UI using tmux and worktrees; Claude Code, Codex, Gemini, Aider, Amp. 8.3k stars, AGPL-3.0. - **Sculptor (Imbue)** ([repo](https://github.com/imbue-ai/sculptor)) - desktop app for parallel Claude Code in isolated workspaces; "experimental research preview," 244 stars, MIT, limited contributions. **Verdict: SKIP.**
- **Agent Orchestrator** ([ComposioHQ repo](https://github.com/ComposioHQ/agent-orchestrator), opened) - open-source, Apache-2.0 orchestrator, about 13.8k stars, with a worker per task in its own worktree, a reviewer agent, and a loop that sends failed checks and review comments back to the owning worker; Claude Code and Codex among 30+ agents. The README page I opened was titled "Orchestrator.inc" while the Augment roundup calls the project "Agent Orchestrator" and says it moved repositories, so confirm the name before installing. The roundup says agents sit idle waiting for tool approval, adding token cost. The CI-fix loop is aimed at feature pull requests, not evidence packets. **Verdict: WATCH.**
- **Warp Oz** ([launch post](https://warp.dev/newsroom/2026/2/10/warp-launches-oz-the-orchestration-platform-for-cloud-coding-agents)) - launched February 10, 2026: cloud agents in Docker sandboxes, schedules, an API, a shareable audit trail per run, and "hundreds of parallel cloud agents." The page does not state pricing or which agents run in it. **Verdict: WATCH.**

### Coordination layers (messaging, leases, claims)

- **MCP Agent Mail** ([original, deprecated](https://github.com/Dicklesworthstone/mcp_agent_mail), [Rust rewrite](https://github.com/Dicklesworthstone/mcp_agent_mail_rust), both opened) - "Gmail for coding agents." Agents get names, inboxes and threads; they take advisory file leases (path or glob, with a time limit so crashed agents release them); a git pre-commit guard refuses commits that touch another agent's reserved files; messages and reservations are written as files in a git archive, with SQLite for search. Works with Claude Code, Codex, Gemini CLI. The Python original (2.2k stars) is in maintenance mode; the Rust rewrite has 150 stars, MIT with an AI-company rider that I did not read, and has been available since October 2025. It runs as an HTTP server (port 8765).
  - Fit: this is the closest published match to problems 1 and 3, because leases plus a pre-commit guard stop two sessions (any vendor) from editing the same file. The catch is the server: sessions in separate ephemeral containers need a shared reachable host, otherwise the leases mean nothing. The git-archive design can be copied with no server by committing lease files (path, owner, expiry) and checking them in a pre-commit or CI guard.
  - **Verdict: WATCH**, and TRY the lease-file design as a small Kean extension.
- **hcom** ([repo, opened](https://github.com/aannoo/hcom)) - MIT; hooks record each agent's activity in a local SQLite database and deliver messages between Claude Code, Codex CLI, Gemini CLI and others, including across machines. 596 stars, 662 commits, regular releases. Hooks work only for agents launched through `hcom`. Fit: live chat among agents on one host; weak for ephemeral container sessions. **Verdict: WATCH.**
- **Ruflo (formerly Claude Flow)** ([repo, opened](https://github.com/ruvnet/ruflo)) - "meta-harness" adding swarms, vector memory and self-learning to Claude Code and Codex. About 80.4k stars. Red flags in the README itself: inconsistent counts ("100+" versus "98" agents; "33 plus 21" versus "35" plugins), self-reported benchmarks in a gist, several claims hedged as "conceptual," mods "not sandboxed," and `init` writes `.claude/` and `CLAUDE.md` into the project, which collides with an immutable codebook. **Verdict: SKIP.**
- **OpenAI Symphony** ([repo, opened](https://github.com/openai/symphony)) - Apache-2.0, 27.9k stars; watches a Linear board, spawns isolated agent runs, returns proof of work (CI status, review feedback) and lands accepted pull requests. Described as a "low-key engineering preview for testing in trusted environments," with an experimental Elixir reference implementation and a spec. The model (tracked item, isolated run, evidence, land) resembles Kean to claim kit, but it needs Linear and a "harness-engineered" codebase. **Verdict: WATCH.** Smaller GitHub-Issues equivalents (Baton, Orbi, sortie) appear in list-only form.

### Loop runners

- **Ralph Wiggum loops** ([Wojcik review, opened](https://tomwojcik-com.pages.dev/posts/2026-01-15/ralph-claude-code); the official Claude Code plugin exists) - a loop that restarts the agent on the same prompt until a done condition is met, with progress held in files. The review: official plugin keeps accumulating context; permission prompts hang an iteration forever; credits can run out silently; tests pass while missing intent because the agent verifies its own work; overnight runs drifted. The author uses autonomous mode only for dependency updates and tightly specified tasks, and moved to a Sonnet implement then Opus review split. Fit: the project already has files-on-disk state and an independent reviewer stage; a loop that self-certifies contradicts the blind-review standard. **Verdict: SKIP.**

### Vendor cloud agents

- **OpenAI Codex (CLI, app, cloud)** (summaries from [IntuitionLabs, updated Oct 2026](https://intuitionlabs.ai/articles/openai-codex-app-ai-coding-agents) and [Vaughan](https://codex.danielvaughan.com/2026/04/08/gas-town-multi-agent-factory/); OpenAI's own docs were blocked, so these are secondary) - desktop app since February 2, 2026 (Windows March 4, Linux preview August 11); subagents (`default`, `worker`, `explorer`, custom TOML) are on by default per the October summary; April guidance gave a default of 6 threads and depth 1; worktrees for parallel tasks; automations; cloud tasks; included in ChatGPT plans, API billed separately. Limits: 59 minutes against 30-60 minute batches leaves no margin; the agent runs outside the project's sealed-packet and hash-checker discipline unless the issue points at a script; I did not verify plan prices or premium-request multipliers.

## Ranked top 5 for this scope

1. **Claude Agent SDK and `claude -p` driver scripts** (ADOPT NOW) - schema-checked output, per-run cost JSON and a hard budget cap for each claim-kit stage; `--bare` with an API key may remove the container login problem (untested).
2. **Claude Code dynamic workflows** (TRY) - one script per batch fanning out drafts and adversarial checks, resumable, with a 1,000-agent cap; Claude-only, so keep the Codex reviewer outside it.
3. **GitHub Agent HQ with issue assignment** (TRY) - one issue as the claim, any of Claude, Codex or Copilot as assignee; fixes duplicate work and gives one audit trail; the 59-minute cap and unverified price are the risks.
4. **Lease-file and claim convention modeled on MCP Agent Mail and Beads** (TRY, small build in Kean) - committed lease files with an expiry, an atomic claim by git push, and a pre-commit or CI guard; addresses collisions between Claude and GPT sessions without a server or a new database.
5. **Codex and Claude headless GitHub Actions (`codex-action`, `claude-code-action`)** (TRY) - run the two independent reviewers as parallel matrix jobs on the existing free runners; I did not open their docs, so verify before relying on this.

Gas Town does not make the list: it is in maintenance mode, its one measured trial failed at about $100 per hour, and its design accepts lost work that this project cannot.
