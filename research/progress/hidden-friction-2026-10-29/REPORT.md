## Diagnosis

The biggest coverage barrier is that 11,569 of the 14,972 currently admitted identities (77.3%) have no adopted provisional status. Status and lifecycle research should proceed together under the existing continuous-assignment rule, with separate exact verdicts and the required adoption review. This is not 11,569 missing texts: the prior claim-kit generation reports held text for 14,884 identities. The census itself is incomplete; finishing these 14,972 does not establish that every EO since 1789 has been found.

Among already statused orders, the large remaining research barrier is clause-specific lifecycle closure: inventory, earliest ending, independent commands, surviving effects and later-source coverage. Old tracker counts include 2,894 inventory/residual blockers and 2,501 first-end blockers, with overlapping categories. Better prompts cannot supply missing evidence or automatically extend a shared conclusion to every command.

The most urgent technical multiplier is **false dependency breadth**: packets and publication attempts depend on global collections even when another worker changes an unrelated case. Repeated corpus reconstruction then makes every retry expensive. Address these before increasing parallel producers.

The current main integrates 91 NRA filed claims and 12 additional Mansfield versions, with four exact Mansfield source-audit holds retained. This is 103 integrated claim versions, not 103 additional ready dossiers. At the final audit check, canonical run [40936647222](https://github.com/D3m0sthene5/Executive-Orders/actions/runs/40936647222) was still in progress at19:23UTC; PR #101 had meanwhile merged. The published 395-ready count comes from the earlier `adcf881ef7eb897e6bec8a8bd7717f4eb3629039` generation. Do not predict a new total by addition.

## What the new NRA work actually teaches

The [NRA report](../../excavator/claude-nira-sweep-2026-10-29/REPORT.md) records 132 attempts, 91 filed reviewed claims, 41 blocks/holds, and 10 caught valid planted controls. Its six-order matched comparison reports 7.018M versus 3.258M weighted producer/reviewer tokens, approximately 53.6% lower per batch. The two groups filed four and five claims respectively. These are small, nonrandomized cohorts with prompt/tool/context differences, not an isolated causal estimate or a whole-project saving.

Ordinary treatment batches T2/T4/T5/T6 attempted 96 orders and filed 64 at about 0.242M weighted tokens per filed claim. Setup and coordinator costs must be charged separately. The report's weighting is uncached input + 1.25 cache-write + 0.1 cache-read + 5 output; it is neither plain token count nor a dollar bill.

There is an important quality exception. T2 treats some report/committee commands as ending with the code provisions; T5/T6 block apparently similar auxiliary commands for lack of an independently demonstrated ending. The cases may differ, but the distinction is not consistently made explicit. Reconcile the actual clauses and evidence, including already filed versions, before using one rule across the family. The shared analysis had separate-context Anthropic review; the prepared cross-family examination was not run. This audit does not independently endorse the legal date or scope.

### Risks worth a bounded test, not established blockers

- **Reservation/publication race:** manual `batch.prepare()` checks existing locks but does not itself acquire a reservation as `kit next` does. Completion's file-set guard and exclusive writes protect important cases; disjoint filenames targeting the same identity still merit a specific race test. No corrupt claim was demonstrated.
- **Fetch cache correctness:** exact-URL cache hits have no automatic TTL/revalidation; reuse of mutable URLs can return a stale capture unless callers explicitly distinguish versions. Immutable captured bytes are valid research evidence when dated correctly. Determine intended semantics per consumer.
- **Fetch retry/eviction:** FetchPool has resumable partial transfers but no general automatic retry in `fetch()`; callers may supply one. Eviction removes individual files rather than atomic body/metadata groups. Consumer-level failure/retry and byte counters are needed before calling this a production bottleneck.
- **Rebuilt packets changing review identity:** genuine source/policy changes should invalidate exact reviews. Distinguish those necessary invalidations from H01/H06 overbreadth; never copy an old attestation onto changed bytes.

## Repair sequence and acceptance evidence

1. **Stabilize concurrent production:** use the existing untracked-in-flight/serial-publication workaround now. Separately resolve A-20261029-1 with a concrete Valla change. Acceptance: unrelated package commits leave packet validity intact; relevant claims, reviews, source bytes and universal policy changes still invalidate; historical package growth cannot stop a bounded query.
2. **Remove multiplicative verification:** verify a packet once per completion invocation; reuse corpus/authority indexes within the same exact snapshot. Acceptance: identical errors and accepted claims, relevant-file add/edit/delete detection preserved, and fewer scans on a real saved multi-member batch.
3. **Stop oversized startup:** narrow initial runner checkout and scope freshness metadata reads. Acceptance: same declared input/output hashes and custody, fewer downloaded/materialized bytes, no missing previous-success generations. Use existing runner tests and a bounded selected-job replay.
4. **Resume high-yield research:** independently settle NRA auxiliary-command scope and the held-source handoffs; process the remaining 208 statused NRA orders with outliers isolated. The 155 unstatused NRA orders can receive continuous research, but adoption requires the current different-family route (A-20261028-4 remains open).
5. **Scale the whole corpus:** route undecided orders by shared evidence and actual source readiness; producer and independent examiner cover status plus lifecycle in one assignment where permitted. Keep historical-census admission work alongside this so the denominator can expand.

Each repair should ride ordinary production and report complete/blocked outcomes, false invalidations, bytes, machine time and available model usage. Do not create another general orchestration system or infer savings from component speed alone.

## How to keep finding these issues without making an audit project

Use existing packet/completion receipts and ordinary runner logs. For each slow/rejected step, ask: what changed, which exact dependencies were rechecked, whether this target used them, how many files/bytes were scanned or transferred, and whether the same snapshot was already verified in this process. Reuse three saved cases: two unrelated concurrent packets, one multi-member supplemented packet, and one undecided batch. Targeted perturbations reveal dependency fan-out; existing source/policy checks prove safety. Add a regression only for a reproduced defect. This is an issue list and acceptance plan, not a new runtime.

Audit execution used one coordinating OpenAI context and three bounded fresh `gpt-6-luna` contexts (inventory/context costs, invalidation/publication, runner/cache). Workers did no legal adjudication. Per-worker tokens, cash and reliable exclusive elapsed time are not exposed in this environment; no cost/savings total is claimed. Only the Valla inventory-count mechanism received a tiny isolated reproduction; other code mechanisms were read, not benchmarked or repaired.
